# ScholarQL — project context for Codex

ScholarQL is a natural-language query engine over research papers, built as a DBMS course project (RVCE) by a team of 3. Users ask questions in plain English; the system turns them into SQL over PostgreSQL, or into semantic search over MongoDB, and shows the answer plus the generated SQL.

Full plan: `docs/ScholarQL_Stack_and_Work_Plan.pdf`. Synopsis: `docs/ScholarQL_Synopsis.pdf`.

## Course rules (must hold)
- Use both SQL (PostgreSQL) and NoSQL (MongoDB), integrated.
- Include an innovative component (here: NLP/AIML, the NL-to-SQL engine).
- At least 5–6 entity types in the ER diagram.
- No PHP for server-side code.

## Stack
- Backend: Python 3.12, FastAPI, Pydantic v2, pydantic-settings, uvicorn
- PostgreSQL via psycopg 3 (async, connection pool); MongoDB via PyMongo `AsyncMongoClient` (not Motor — deprecated)
- Embeddings: fastembed with `BAAI/bge-small-en-v1.5` (384 dimensions, CPU/ONNX, no PyTorch)
- LLM (Person B): Gemini Flash via `google-genai`, Llama via `groq`; SQL validation with `sqlglot`
- Resilience: `tenacity` (retries), `slowapi` (rate limits)
- Frontend: Next.js (App Router) + TypeScript + Tailwind + shadcn/ui, `@tanstack/react-query`, `@tanstack/react-table`, `openapi-typescript` + `openapi-fetch`, `recharts`
- Local dev: Docker Compose with `postgres` and `mongodb/mongodb-atlas-local` (supports Vector Search locally)
- Tooling: uv (Python), pnpm (JS), Ruff, pytest, GitHub Actions
- Hosting (later): Vercel (web), Render (API), Neon (PostgreSQL), MongoDB Atlas M0 (max 3 search/vector indexes)

## Contracts (agreed with the team — do not change shapes without asking)
1. **SQL schema** (A, frozen end of week 1): tables `paper`, `author`, `venue`, `institution`, `topic`, `authorship`, `citation`. Read-only role `scholarql_reader`.
2. **API spec** (C): generated by FastAPI from `api/app/models/`. The web app's types in `web/lib/api.ts` are generated from it.
3. **Engine interface** (B): `answer(question: str) -> Answer` with fields `sql`, `columns`, `rows`, `route`, `explanation`, `attempts`, `latency_ms`.
4. **MongoDB shapes + vector search** (C): `vector_search(text, k, filters) -> list[(paper_id, score)]`.
   - `paper_content`: `_id` (= paper_id), `abstract`, `tldr`, `embedding` (384 floats), `year`, `venue_id`
   - `author_profiles`: `_id` (= author_id), `name`, `institution_id`, `embedding`, `paper_ids`
   - `query_logs`: `question`, `sql`, `route`, `ok`, `latency_ms`, `feedback`, `created_at`
   - Input file from A: `papers_content.jsonl`, one JSON per line with `paper_id`, `abstract`, `tldr`

**Shared ID rule:** every paper, author, venue, institution and topic uses its numeric OpenAlex ID (e.g. W2741809807 → 2741809807) as its key in BOTH databases.
